\begin{abstract}
Passing a physical USB device through to a virtual machine (VM) is attractive
for storage, dongles and instrumentation, but it conflicts with live migration:
the host-side device session (open file descriptors, claimed interfaces,
endpoint state and the device's internal state) cannot be serialised, so any
migration path that tears the session down forces the guest to re-enumerate.
This paper studies the concrete case of Cloud Hypervisor together with
\code{usbvfiod}, a Rust vfio-user server that emulates an eXtensible Host Controller Interface (xHCI) controller. We
first show, by measurement, that migrating a VM with a vfio-user device
\emph{deadlocks}: the destination blocks for $199.9$\,s inside the protocol
version handshake because the vfio-user server accepts exactly one connection,
which the source still holds. We then present a design that removes the
deadlock without modifying any virtual machine monitor (VMM) source file: because
the vfio-user handshake commands
never touch the device backend, a wrapper that takes the backend lock
\emph{per command} rather than per connection lets a second client connect
while the first client is still connected. A separate one-line bug in the
protocol crate (an inverted reset-capability test) does require rebuilding the
VMM against the fixed crate, because the crate is compiled into it. We identify
and fix two defects that the hand-over exposes---a departing client tearing down
the surviving client's interrupt line and DMA mappings, and completion
interrupts lost inside the hand-over window---and we describe a measurement
harness that derives the verdict from the
guest's own log rather than from host-side observation.
On a real 32\,GB exFAT stick passed through to an Ubuntu 22.04 guest, a
128\,MiB file copy that spans the migration completes in \PassCount{} out of \TotalRuns{} runs with a measured downtime of \DowntimeMin--\DowntimeMax\,ms, byte-identical data and, at the USB
level, no re-enumeration, no reset and no I/O error in the guest. A
no-migration control, a release-build arm, a kick-disabled negative control and
a naive detach/re-attach baseline separate the fixes from the conditions; the
kick-disabled arm alone is not statistically conclusive on its own, so a
fault-injection suite that enlarges the hand-over window on purpose is what
shows both hand-over fixes to be load-bearing rather than incidental.
\end{abstract}

\section{Introduction}
%=====================================================================

Virtual machines are routinely equipped with physical devices through
passthrough so that they can use hardware that is either impossible or
unattractive to emulate. Live migration---moving a running VM between VMM
instances with a downtime short enough to be unnoticeable---is the standard
mechanism for host maintenance, load balancing and upgrades
\cite{clark2005live}. The two techniques, however, interact badly.

Memory and CPU state migrate well, and in-kernel VFIO devices can migrate when they implement the VFIO device
migration interface \cite{vfiomigrationuapi}. USB
devices are harder, because the host-side session is not part of the guest
state. A guest talks to a USB device through a host
controller; a passthrough implementation either emulates that controller and
forwards individual transfers, or hands the whole controller to the guest. In
the first case the host process that owns the physical device holds a session
that is \emph{not} part of the guest state: an open file descriptor, a claimed
interface, endpoint configuration and, above all, the device's own internal
state. None of this can be serialised. Any migration that recreates the device
on the destination therefore forces the guest to observe a disconnect and a
re-enumeration, which at minimum interrupts I/O and can invalidate host-side
state such as a mounted filesystem or an encrypted volume.

Cloud Hypervisor (CH) supports USB passthrough through the vfio-user protocol
via \code{-{}-user-device socket=...} \cite{chvfiouser}. The server side can be
\code{usbvfiod} \cite{usbvfiodrepo}, which emulates an xHCI controller and
forwards transfers to the physical device with \code{nusb} \cite{nusb}. CH
documents live migration \cite{chlive}, but the vfio-user path was never
exercised under migration.

This paper starts from a measurement: migrating a CH VM that has a vfio-user
device attached does not fail cleanly---it \emph{hangs}, and it hangs on the
destination VMM (Section~\ref{sec:problem}). We then design and implement a
solution that makes a same-host migration of such a VM work, and we measure it
end to end with real hardware.

\subsection{Contributions}
\begin{enumerate}
  \item We characterise, by measurement and source inspection, why a
        vfio-user device deadlocks a CH live migration: the destination VMM
        blocks in the version handshake because the server accepts a single
        connection that the source still holds. We quantify it (199.9\,s of
        zero progress; the destination never gets a reply) and show that even a
        successful takeover would not transfer device state
        (Section~\ref{sec:problem}).
  \item We present a \emph{multi-client} vfio-user backend design that removes
        the deadlock without modifying the VMM. The key observation is that the
        handshake commands never reach the device backend, so the backend lock
        can be taken per command instead of per connection
        (Section~\ref{sec:design}).
  \item We identify and fix two defects that only appear once a hand-over is possible---a departing client disabling the surviving client's interrupt line and unmapping its DMA regions, and completion interrupts being delivered to the departing VMM's interrupt descriptor inside the hand-over window (Sections~\ref{sec:ownership} and~\ref{sec:interrupt})---and a reset-capability parsing bug in the protocol crate that made every connection reset the device (Section~\ref{sec:crate}).
  \item We build a reproducible end-to-end harness, including a guest image
        and a measurement method whose verdict is read from the \emph{guest's
        own log} rather than from host-side observation, and we report the
        design decisions that this method forced us to change
        (Section~\ref{sec:implementation}).
  \item We evaluate the result with a real USB stick: \PassCount{} out of
        \TotalRuns{} migrations of a VM that is copying a 128\,MiB file at the
        time of the migration succeed with \DowntimeMin--\DowntimeMax\,ms
        downtime, byte-identical data and no re-enumeration or reset in the
        guest, and we separate the fixes from luck with a no-migration control,
        a release-build arm, a kick-disabled negative control, a naive
        detach/re-attach baseline, and a fault-injection suite that makes the
        hand-over race happen by construction
        (Sections~\ref{sec:evaluation}--\ref{sec:injection}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:background}
%=====================================================================

\subsection{Live migration}
Live migration of VMs was popularised by Clark \emph{et al.}
\cite{clark2005live}, who introduced pre-copy migration: pages are copied
while the VM runs, and a final stop-and-copy phase transfers the remaining
dirty pages while the VM is paused. KVM \cite{kivity2007kvm} made this a
mainstream kernel mechanism, and modern VMMs such as Firecracker
\cite{agache2020firecracker} and Cloud Hypervisor \cite{chrepo} implement
variants of it. Cloud Hypervisor documents both TCP and UNIX-socket transports;
for same-host migration it offers \code{memory\_mode=memfds}, which passes the
guest memory \emph{backing file descriptors} (\code{memfd}, \cite{memfd}) over
the socket so that source and destination map the same memory instead of
copying it \cite{chlive}. This is
the mode we use: it makes the memory identical in both VMMs, which is what
allows a vfio-user server on the host to keep its DMA mappings.

\subsection{Device passthrough: VFIO and vfio-user}
VFIO is the Linux framework that exposes a device to user space with an
IOMMU-backed DMA model \cite{kernelvfio}. In the kernel-VFIO model the VMM maps
device BARs and registers event descriptors directly. vfio-user moves the same
programming model to a user-space server reached over a UNIX socket
\cite{qemuvfiouser}: a client (the VMM) queries regions, reads and writes
device memory, maps guest memory for device DMA, registers interrupt file
descriptors, and may reset the device. The protocol specification is maintained
with QEMU \cite{qemuvfiouser} and reference implementations exist in
\code{libvfio-user} \cite{libvfiouser}. Cloud Hypervisor implements the client
side \cite{chvfiouser}; the \code{vfio\_user} crate \cite{vfiousercrate}, part
of the rust-vmm collection \cite{rustvmmvfio}, implements both sides and is
used by CH and by \code{usbvfiod}.

Two lines of work are directly adjacent to ours. A QEMU patch series proposes
protocol-level live migration for vfio-user devices by reusing the generic VFIO
v2 migration infrastructure---migration data read/write and DMA logging for
dirty-page tracking \cite{komatsu2026vfiousermig}. That is the right long-term
answer, and it is \emph{not} what this paper does: it transfers device state, which
requires both ends to run a compatible server and does not preserve a host-side session that cannot be expressed as state. Our problem is the same-host case,
where the server process can simply stay alive and only the VMM that talks to
it changes; what we contribute there is the removal of the connection-level
serialisation that otherwise makes the hand-over impossible, plus the
hand-over correctness rules that a state-transfer design would also need. The
second line is earlier work on migrating USB devices between hosts through a
proxy mechanism \cite{watanabe2010usbglobal}, which likewise assumes a
medium that carries the device rather than preserving a local session.

\subsection{USB passthrough alternatives}
Table~\ref{tab:approaches} compares the options we considered. Passing through
with a user-space server over vfio-user is the approach of \code{usbvfiod} and
the subject of this paper: it keeps the guest driver unmodified and confines
the device to an unprivileged process, at the cost of an emulated controller in
the transfer path. USB/IP \cite{hirofuchi2005usbip,kernelusbip} tunnels USB
traffic over a network and is the natural answer for \emph{cross-host} device
sharing, but the device remains attached to the source host and depends on an
external transport. QEMU also provides USB to a guest, either by emulating
devices or by attaching a physical one with \code{usb-host} \cite{qemuusb}.
Libvirt does permit a domain with a USB host device to migrate
\cite{libvirtmigrationsrc}: its source comment calls the USB case ``migrated''
in quotation marks, and QEMU's \code{usb-host} realises that by detaching the
device on the source and re-attaching it on the destination. The host-side
session is not preserved: the guest sees the device
disappear and come back, which is exactly the naive alternative we measure in
Section~\ref{sec:baseline}. USB redirection sends the traffic to a remote client
\cite{usbredir} rather than preserving a host-side session.

\subsection{Emulated xHCI and USB mass storage}
\code{usbvfiod} presents an xHCI controller \cite{xhcispec} to the guest. The
Linux xHCI driver discovers the controller, performs a host controller reset,
enumerates the attached devices and then drives transfers through command,
event and transfer rings in guest memory. Mass-storage devices use the
Bulk-Only Transport protocol \cite{usbbot}, which the kernel's
\code{usb-storage} module implements. Our measurements use this path because it
is the most common passthrough workload and because a bulk transfer makes the
consequences of a lost completion immediately visible as an I/O error.

Figure~\ref{fig:arch} summarises the resulting architecture. The physical device
is owned by a host process for the entire lifetime of the VM, including the
migration; the VMM is only a client of that process, and the guest sees an
ordinary controller.

\subsection{Experimental setup}
\label{sec:setup}
All measurements were taken on one bare-metal host running Debian~13 with
Linux 6.17.4 (Proxmox kernel), 8 cores and 62\,GiB of RAM, which runs the Kernel-based Virtual Machine (KVM). The
host was \emph{not} idle: four unrelated KVM virtual machines (16, 8, 2 and
1\,GiB of RAM) were running throughout, and no CPU pinning was used. We report
this because it is an uncontrolled load confounder and, as
Section~\ref{sec:results} notes, the most likely explanation for the spread in
the measured downtime. Table~\ref{tab:setup} lists the software under test. The
guest has 2\,GiB of RAM and one vCPU, runs Ubuntu 22.04.4 (kernel
5.15.0-94-generic) and is booted directly by CH. The physical device is a 32\,GB
USB~2.0 High-Speed stick (Innostor \code{1f75:0903}, exFAT data partition)
attached at \code{/dev/bus/usb/001/007}. The server binary under test was an
unoptimised \code{cargo} debug build, run with verbose logging
(\code{-v}) and USB packet capture enabled; Section~\ref{sec:threats}
discusses the resulting measurement overhead.

\subsection{Measured baseline: the migration deadlocks}
Figure~\ref{fig:deadlock} illustrates what we measured. A source VM with
\code{-{}-user-device socket=...} is migrated with \code{send-migration} using
\code{destination\_url=unix:...} and \code{memory\_mode=memfds}. The
destination VMM starts from the migrated configuration and reaches the point
where it restores the vfio-user device:

\begin{quote}\footnotesize\ttfamily
device\_manager.rs:4749 Restoring virtio-pci \_vfio\_user0 resources
\end{quote}

\noindent and then makes no further progress. We waited 199.9\,s; there was no
additional log output, no error, and the destination VMM's control API stopped answering.
The source VM remained paused in the migrating state. This measurement predates
the fixes and comes from the standalone phase-0 experiment recorded in the
project's development log (the round-3 batches of Section~\ref{sec:evaluation}
measure the fixed system and do not contain it). Three observations pin
the cause down: the server logged exactly \emph{one} client version handshake
(the source's), a socket inspection showed \code{Recv-Q=1} on the listening
socket, i.e.\ the destination's connection was established but never accepted,
and the destination had blocked inside

\begin{quote}\footnotesize\ttfamily
pci/src/vfio\_user.rs:4338 $\rightarrow$ vfio\_user::Client::new()\\
\phantom{pci/src/vfio\_user.rs:4338 $\rightarrow$ }$\rightarrow$ negotiate\_version() $\rightarrow$ read\_exact()
\end{quote}

\noindent waiting for a reply that never comes.

\begin{figure*}[t]
\centering
\input{figures/deadlock.tex}
\caption{Measured deadlock of the unmodified stack. The vfio-user server calls
\code{accept()} exactly once, so the destination's connection is queued and its
version handshake is never answered; the migration never completes.}
\label{fig:deadlock}
\end{figure*}

\subsection{Root cause: one connection, one accept}
The server side of \code{vfio\_user}~0.1.5 serves a connection by calling
\code{listener.accept()} once and then looping over commands until the peer
closes. A second client therefore \emph{connects successfully} (the kernel
completes the handshake into the listen backlog) but is never served, which is
exactly the ``hangs forever'' symptom above. A cross-host migration would have
the same problem, and additionally the destination would have no device: the
guard for that exists only for kernel-VFIO devices
(\code{VFIO device does not support migration}), not for vfio-user.

\subsection{Device state would not be transferred anyway}
Even with the hand-over solved, the vfio-user device carries almost no migration state in this version. Its \code{Pausable}, \code{Transportable} and
\code{Migratable} implementations are empty, and its snapshot contains only the
generic PCI state (configuration space, INTx/MSI/MSI-X configuration and the
MSI-X table); device BAR state, opaque device state and DMA dirty tracking are
absent. There is no device-state region in the protocol implementation and no
parameter with which the destination could be pointed at a different vfio-user
server. A protocol-level migration mechanism has been proposed for vfio-user \cite{komatsu2026vfiousermig}, but the implementation used here
carries no device state. This is why our design deliberately does
\emph{not} try to move device state: for a same-host migration the server
process simply stays alive and keeps the session, and only the \emph{client}
that the server talks to changes.

%=====================================================================
\section{Design}
\label{sec:design}
%=====================================================================

\subsection{Goals and non-goals}
The goal is that a same-host live migration of a VM with a passed-through USB
storage device completes, and that the guest does not observe a device change.
Concretely we require: (i) the migration completes; (ii) the guest sees no
re-enumeration and no reset; (iii) data transferred across the migration is neither corrupted nor lost
(duplication is not tested, as Section~\ref{sec:threats} explains); (iv) the VMM needs no source change, being only rebuilt against the fixed
protocol crate. Non-goals are cross-host migration, USB classes
other than bulk storage, and isochronous transfers.

\subsection{Multi-client backend with a per-command lock}
The deadlock exists because the server serialises \emph{connections} even
though the commands it handles are mostly independent of the device. In the
crate, only \code{RegionRead}, \code{RegionWrite}, \code{DmaMap},
\code{DmaUnmap}, \code{SetIrqs} and \code{DeviceReset} invoke the backend;
\code{Version}, \code{DeviceGetInfo}, \code{DeviceGetRegionInfo} and
\code{GetIrqInfo} do not. Consequently a second client can complete its
handshake while the first is still attached, provided that the backend is
shared with a lock taken \emph{per command}.

Figure~\ref{fig:multiclient} shows the resulting structure. A shared state object
owns the backend and the interrupt-ownership bookkeeping, and hands out one
handle per connection. Each handle implements the server backend trait by
delegating to the shared backend under a mutex for the duration of a single
call. The accept loop is replicated over a configurable number of threads, so
the process can serve the source and the destination simultaneously. The
default keeps the historical single-client behaviour unchanged, which matters
for the systemd integration where the server is expected to exit when its only
client goes away.

\centering
\input{figures/multiclient.tex}
\caption{Multi-client backend. Handshake commands never take the lock, so the
destination VMM can connect while the source is still attached; the device
state itself lives in the shared backend and therefore survives the hand-over.}
\label{fig:multiclient}
\end{figure*}

\subsection{Ownership: a departing client must not tear the device down}
\label{sec:ownership}
Allowing two clients exposes a hazard that a single-client server never had.
When the migration completes, the \emph{source} VMM shuts its device down and
sends two destructive commands: \code{SetIrqs} with an empty descriptor list
(disable interrupts) and \code{DmaUnmap} for the regions it mapped. Both arrive
\emph{after} the destination has already registered its own interrupts and DMA
mappings, and both would be applied to the shared backend. The result we
measured is severe: the destination is left with a dummy interrupt line, no
completion is ever signalled, the guest's commands time out and the running I/O
fails. Section~\ref{sec:injection} reproduces exactly this by disabling the
guard on purpose: five runs out of five fail, with a 36\,s command timeout and
repeated I/O errors in the guest's kernel log.

The wrapper therefore tracks which connection most recently registered
interrupts and lets only that connection issue the destructive counterparts.
Teardown from any other connection is logged and ignored. In every run we
observed the interrupt-disable half of this guard fire (the server logs the
ignore); we did not observe a \code{DmaUnmap} reach the server on this path, so
that half is implemented but not exercised by our workload. This is deliberately
coarse: it is correct for the hand-over case, which is the case that needs it,
and it cannot be triggered accidentally by the active client.

\subsection{Interrupt hand-over correctness}
\label{sec:interrupt}
A subtler, timing-dependent defect remains even after
Section~\ref{sec:ownership}. The interrupter signals every event by writing to
the currently installed interrupt line. During a hand-over there is a window in
which a transfer may complete \emph{before} the destination's line is
installed: the completion event is written into the guest's event ring (which
is in guest memory and therefore already correct), but the interrupt is
delivered to the event descriptor of the VMM that is exiting. If that completion
is the last one outstanding, the guest never learns that it completed---it does
not re-read its event ring without an interrupt---and the copy stops at a fixed
byte count until the block layer's command timeout expires; in our failing runs
that produced repeated I/O errors rather than a recovery. If more commands were
still queued, the next completion interrupts the guest on the new line and the
guest drains the ring, including the event it was not told about. That is why
the defect is intermittent, and why it is established in this paper by injection
rather than by repeating natural runs (Section~\ref{sec:injection}).

Our fix is to re-raise one interrupt immediately after a new line is installed.
A spurious MSI-X interrupt is harmless: the guest inspects the event ring,
finds the pending completion (or nothing) and continues. This converts a lost
interrupt into at most one redundant ring scan, and the 5\,s-window experiment
shows that one such interrupt is sufficient even when the window is two to
three orders of magnitude wider than the natural one.

\subsection{DMA mapping idempotence}
\label{sec:dma}
Because source and destination map the \emph{same} guest memory under
\code{memory\_mode=memfds}, the destination re-issues \code{DmaMap} for ranges
that the source already mapped. A naive ``insert only'' bus rejects the
duplicate as an overlap. We make the DMA bus replace a mapping that starts at
the same address, while still rejecting a genuine overlap at a different
address, and we make a failed insert leave the bus untouched. We also implement
the unmap path, which the VMM invokes when it destroys a device and which was
previously unimplemented.

\section{Implementation}
\label{sec:implementation}
%=====================================================================

\subsection{usbvfiod}
The multi-client change is 381 added and 28 removed lines over six files in the
pull-request branch (the hand-over fixes were reviewed separately): a new
\code{shared\_backend} module
implementing the wrapper and the ownership rules; the accept-loop and lifecycle
logic in \code{main.rs}; a \code{-{}-max-clients} option; the idempotent DMA
bus; and the DMA, reset and interrupt-registration paths of the xHCI backend.
Two further changes are small but load-bearing: moving the hand-over kick into
the interrupter worker, and the two debug-only injection hooks used in
Section~\ref{sec:injection}. The working tree as a whole differs from
the upstream revision by seven files (516 added and 104 removed lines); six of
those files, i.e.\ everything except the interrupter, are 483/103. The
device emulation itself is untouched. Unit tests grew by three (108 to 111 test
attributes; \code{cargo test} reports 112 passing),
and the project's strict lint configuration (\code{clippy} with all, nursery and
cargo groups denied) passes.

\subsection{Protocol crate}
\label{sec:crate}
One behavioural bug in \code{vfio\_user}~0.1.5 had to be fixed for the reset
semantics to be sane. The client parses the device's reset capability by
comparing the masked flag word with \emph{inequality}, which inverts the result:
a server that advertises ``not resettable'' is reported as resettable, so the
VMM issues a device reset on every connection, including on the destination's
connection during a migration. The fix is a one-line equality comparison. Because the
crate is consumed by the VMM, the fix is applied to the VMM's dependency graph
rather than to \code{usbvfiod}, which only uses the server side.

We should be explicit about what this fix is and is not supported by. It is
established by inspection of the published crate and by the behaviour of the
unpatched build, in which CH's destination-side device creation fails and the
experiment cannot run at all; that is why every measurement in this paper uses
the patched build. It is \emph{not} isolated by an ablation arm: no log in the
round-3 batches contains a \code{DeviceReset} command, because with the fix in
place the reset is not offered and therefore never issued. A controlled
comparison would require an arm that patches the parse to force a reset, which
we did not run, so the claim we make is the narrow one---the parse is inverted
and the build with it corrected is necessary to obtain the results here---rather
than a measured statement about how much the reset alone costs.

\subsection{Cloud Hypervisor integration}
No CH source file was modified, but the result does require a \emph{custom CH
build}: the integration artefact is a \code{[patch.crates-io]} entry that
points CH at the fixed crate, and reproduction therefore needs that build. Because the
crate lives in a monorepo whose manifest also references a sibling
\code{vfio-bindings} crate that has diverged from the published version, the
patch deliberately uses a variant of the fix branch in which that crate resolves
from crates.io; otherwise two copies of \code{vfio-bindings} coexist and their
types no longer unify. This is a build-level detail, not a design change, and it
is documented so that it can be dropped once the fix is released upstream.

\subsection{Guest image and measurement harness}
Measurement honesty turned out to require as much care as the device code, and
we record the decisions because they changed our verdict twice.

\emph{Guest image.} The Ubuntu live-server ISO cannot be booted directly: its
initrd insists on finding a live medium and ignores \code{root=}, and the
minimal squashfs ships an empty \code{/lib/modules}, so \code{usb-storage}
cannot be loaded after the switch. We therefore unpack the ISO, graft the
module tree out of the initrd, rebuild the initrd without the casper hooks and
pack a bootable ext4 image. The exFAT driver, which real sticks use, lives in \code{linux-modules-extra} and is merged in explicitly.

\emph{Console capture.} CH opens a serial \code{file=} target with
\code{File::create()}, so the destination VMM truncates the log when it starts;
the pre-migration evidence disappears exactly when it becomes interesting. We
capture the console through a FIFO kept open by a reader that never sees EOF.

\emph{Verdict source.} The migration also re-creates the destination's serial
device, which resets the guest TTY. Progress written only to the console then
looks like a hang although the guest is fine. We therefore make the guest log
to a file and treat the serial console as a best-effort mirror, and we compute
the verdict from the guest's own log after stopping the VMs and mounting the
disk image---with the journal replayed, because a read-only \code{noload} mount
hides the most recent writes. A guest heartbeat service, finally, distinguishes
``guest frozen'' from ``console broken'', and reports the size of the in-progress
copy so the harness can place the migration at a fixed fraction of the transfer
rather than after a fixed wall-clock lead.

\emph{Fault injection.} Two hooks in the server exist only in debug builds and
only take effect when an environment variable is set, so an ordinary run cannot
reach them: one sleeps for a configured number of milliseconds inside the
\code{SetIrqs} handler \emph{before} the new interrupt line reaches the
interrupter worker, and the other makes every connection believe it owns the
device, which reintroduces the stale-teardown defect. They are what turns the
hand-over window from a race that happens by chance into one that happens by
construction; Section~\ref{sec:injection} uses them, and the first row of that
section's table checks that they are inert when unset.

\subsection{Methodology}
The workload is a 128\,MiB file copied from the passed-through stick to the
guest's own disk with \code{dd}, in a systemd unit that starts at boot. The
harness waits until the guest reports that it has copied 16\,MiB---a fixed
\emph{fraction} of the file, read from the copy progress the guest puts in its
heartbeat, rather than a fixed wall-clock lead---and then requests the
migration. A wall-clock lead is not portable across builds: the release build
copies the same file several times faster than the instrumented debug build, and
a lead tuned for one lets the copy finish before the migration is even requested.
A run is successful only if
all four of the following hold: the copy window strictly contains the
\emph{whole} migration, from the request to the completion of the switchover
(the request is recorded by the harness and the completion is taken from CH's own log); the MD5 of the copied file equals the MD5 of
the source file on the stick; the guest shows no enumeration after the migration
uptime; and no reset or I/O error appears. The MD5 comparison is made inside the
guest against the stick itself, so it also verifies that the device remained
readable after the migration. The migration was requested with CH's
\code{downtime\_ms=300} as the per-iteration stop-and-copy goal; the separate
project acceptance target, used for the verdict, was $\le 2000$\,ms. All runs
were executed consecutively on the same host with the same stick and the same
128\,MiB file, whose content was generated once and never regenerated between
runs.

A single arm cannot separate the effects that a migration experiment confounds,
so the acceptance arm (\TotalRuns{} runs of the fixed system, debug build) is
accompanied by four further arms which differ in exactly one factor:
\ControlRuns{} runs with no migration at all (does the workload alone produce the
result?), \ReleaseRuns{} runs with the release build (is the debug build's
instrumentation doing the work?), \KickOffRuns{} runs with the hand-over kick
disabled (is the kick load-bearing?), and three runs of the naive alternative in
which the device is detached and re-attached with the hotplug interface instead
of migrating. Section~\ref{sec:injection} adds a fault-injection suite that
makes the hand-over race happen by construction, so that the fixes can be
credited rather than merely not falsified.

\subsection{Results}
\label{sec:results}
All \TotalRuns{} runs pass. Table~\ref{tab:results} lists the per-run figures;
Figure~\ref{fig:downtime} shows the downtime distribution. Downtime is measured
by CH (\code{downtime\_ms}), not by the harness. Copy duration is the time the
guest takes to copy the file, which is chosen to be long enough that the
migration necessarily falls inside the copy window.

\emph{How much does \PassCount{} out of \TotalRuns{} establish?} More than the
ten-run version of this experiment did, but still not much on its own, and we
prefer to say so. \TotalRuns{} consecutive successes give a one-sided 95\,\%
lower confidence bound of $\PassLowerOneSided$ on the pass probability and a
one-sided 95\,\% upper bound of $\FailUpper$ on the residual failure rate; the
two-sided 95\,\% Clopper--Pearson interval is $[\CILow, \CIHigh]$. Against the
pre-fix behaviour we observed---one failure in five runs---the comparison is
still not statistically significant (two-sided Fisher exact, $p=\FisherPreFix$ against the
five-run arm). \TotalRuns{} successes bound the residual rate at roughly one in
seven; they do not by themselves show \emph{which} fix carries the weight. That
is what the negative controls and the injection suite of
Sections~\ref{sec:arms}--\ref{sec:injection} are for, and
Section~\ref{sec:threats} discusses what would be needed to narrow the bound
further.

\emph{What power do the comparisons have?} We report this rather than leaving it
implicit. Taking the observed rates as the truth, the natural kick comparison
(\KickOffPass/\KickOffRuns{} against \PassCount/\TotalRuns) has exact
unconditional power $\PowerKickNatural$ at the sample sizes we used; reaching
80\,\% power against the same effect would need about \NKickForEighty{} runs per
arm, which is why we did not try to settle the kick question with more natural
runs and instead used the injection suite. The 5\,s injection pair is discussed
in Section~\ref{sec:injection}, including the power it does and does not have.

\emph{Was the hand-over path actually exercised?} Yes, in every run, and the
harness records it. Each run shows two interrupt-line installations (the source
registering at start-up, the destination taking over during the migration) and
one re-raised interrupt per line installation (the same count in every run,
\KickMin{}, the second of which is on the destination's hand-over line), and one
stale teardown that the
server refused (the same count in every run, \StaleMin{}, logged as
\code{ignoring IRQ disable from stale vfio-user client}). Without that refusal
the destination would have been left with a dummy interrupt line, which is the
failure mode we measured before the guard existed. The counts come from the
server log of each run, which is archived with the raw data.

The downtime figures are also less precise than their range suggests: the median
is \DowntimeMedian\,ms but the bootstrap 95\,\% interval for the median is
$[\DowntimeMedianCILow,\DowntimeMedianCIHigh]$\,ms, against an observed range of
\DowntimeMin--\DowntimeMax\,ms. The \TotalRuns{} values are not unimodal:
eleven runs give 4--6\,ms, eight give 15--21\,ms and one gives 10\,ms, and the
groups alternate rather than drift (runs 1--2 give 18 and 19\,ms, runs 3--4 give
5 and 6\,ms, runs 5--6 give 17 and 15\,ms). We cannot attribute this to the
co-resident VMs of Section~\ref{sec:setup} as we first assumed: joining the
archived host-load samples to each run (the last sample at or before the
migration instant) gives a slightly \emph{negative} correlation between the
one-minute load average and downtime
($r=-0.38$ for the acceptance arm; the high-downtime runs average a lower load
than the low-downtime ones), which points more to the switchover cost depending
on the device and queue state than to host CPU. The one-minute load average is
also too coarse to resolve a few-millisecond stop-and-copy phase, so we report
the pattern and the failed hypothesis rather than a cause. It is anyway not a
property of the USB path, which is idle during the switchover.
Copy duration varied between \CopyMin\,s and \CopyMax\,s; the no-migration
control (\ControlRuns{} runs, median \ControlCopyMedian\,s) shows the same
spread, so we do not attribute that variation to the migration.

\subsection{Controls and negative controls}
\label{sec:arms}
Table~\ref{tab:arms} puts the acceptance arm beside three comparison arms (a fourth, the naive detach/re-attach baseline, is reported separately in Section~\ref{sec:baseline}).
Two of them bound our claims from opposite sides.

\emph{No migration.} The \ControlRuns{} control runs copy the same file on the
same guest without migrating. All complete with matching checksums, so the
workload by itself is sound and the copy-duration spread is not caused by the
migration. Because there is no migration, these runs are judged on the digest
alone: the span, enumeration and downtime criteria do not apply, and the arm
cannot rule out a guest-visible disturbance that leaves the final digest intact.
These runs deliberately have no downtime figure either.

\emph{Kick disabled.} The \KickOffRuns{} runs use the acceptance build with the
hand-over interrupt suppressed by a debug-only environment switch. This is the
arm that decides whether the kick earns its place: if these runs failed at the
rate suggested by the exposure measurement, the kick would be clearly
load-bearing; if they all passed, it would be defensive decoration. The outcome
is in between---\KickOffPass/\KickOffRuns{} pass, one run stalls at a fixed byte
count with no re-enumeration; its guest console shows no error until the block
layer's command timeout fires about 30\,s later, and the copy never reports
completion, which is the lost-completion signature---and on this sample alone the
difference from the acceptance arm is
not significant (two-sided Fisher exact, $p=\FisherKick$). The reason is structural rather
than statistical: a missed completion is only fatal when it is the last one
outstanding (Section~\ref{sec:exposure}), so an arm that leaves the window to
chance can only fail in the fraction of runs where that coincidence occurs.
Section~\ref{sec:injection} therefore removes the luck by enlarging the window by
construction.

\emph{Release build.} The \ReleaseRuns{} release runs copy at a median of
\ReleaseCopyMedian\,s against \CopyMedian\,s for the debug build; the
instrumentation (tracing at \code{-v}, packet capture) therefore slows the
transfer noticeably but does not change the outcome, which is what matters for
the argument. All \ReleasePass{}/\ReleaseRuns{} pass.

\subsection{The naive alternative: detach and re-attach}
\label{sec:baseline}
The obvious way to move a passed-through device to another VM without changing
the host-side server is to let the host-side session go and make a new one:
detach the device, then attach it again. We measured what the guest sees in that
case with the same workload and the same guest-log criteria, replacing the
migration with a hotplug detach four seconds into the copy and a re-attach five
seconds later.

In all \ReplugRuns{} baseline runs the copy failed. The guest's own kernel log
records \code{usb 1-1: USB disconnect, device number 2} at the detach moment,
followed by up to \ReplugIOErrMax{} \code{blk\_update\_request: I/O error} lines
for reads that were in flight on \code{sda}; \code{dd} returned non-zero in
every one of the \ReplugRuns{} runs and the digest of the partial file matched
the source in \ReplugDigestMatch{} of them. No re-enumeration appears in any of them. That is an observation rather than
an artefact of the run ending: the guest keeps heart-beating for about twenty
seconds after the re-attach, and the device still does not come back, while the
copy has already failed with a non-zero status.

That is the cost the design avoids, and it is the same class of event as the one
Section~\ref{sec:problem} attributes to tearing the session down---but here the
guest sees it directly. It also shows why ``detach and re-attach'' is not an
acceptable implementation of the same-host hand-over: it does not merely disturb
the guest, it fails the transfer.

\subsection{How exposed the runs were to the race}
\label{sec:exposure}
The hand-over fix only matters if the race it addresses actually occurs, so we
measured its exposure instead of inferring it. Two things have to coincide: a
transfer must complete while the source VMM will never service another
interrupt, and before the interrupter has installed the destination's line. The
server log records every completion and every line installation with microsecond
timestamps, but the start of the window is not directly observable: the harness
records the migration epoch just before it launches \code{ch-remote}, CH
pre-copies so the guest keeps running for a few milliseconds after the request,
and the pause is logged on CH's own clock. We therefore report three anchors
rather than one, because the answer depends on which is used.

The end of the window is the second interrupt-line installation, which is
exact. For the start we cross-tie CH's uptime to wall clock within each run using
two causally adjacent event pairs---CH's \code{Enabling IRQ} against usbvfiod's
first \code{set IRQs}, and CH's \code{Disabling IRQ} against the
\code{ignoring IRQ disable} line---which agree to within 0.2\,ms in every run.
Anchoring the pause on CH's own clock gives the lower bound (\ExposureRuns{} of
\ExposureMeasured{} runs, \ExposureCompletions{} completions, window
\ExposureWindowMin--\ExposureWindowMax\,ms); anchoring it through the harness
epoch gives \ExposureEpochRuns{} runs and \ExposureEpochCompletions{}
completions (window \ExposureEpochWindowMin--\ExposureEpochWindowMax\,ms); and
using the harness epoch itself as the start of the window---it is recorded
before \code{ch-remote} is even launched---gives the strict upper bound of
\ExposureUpperRuns{} runs and \ExposureUpperCompletions{} completions
(\ExposureUpperRate\,\%, window up to \ExposureUpperWindowMax\,ms). All three are
in the same range: the race occurs naturally in a minority-to-half of the
acceptance runs, and every completion counted in the window is a transfer
completion (the events are \code{Transfer} TRBs, not command or port events).
For each of them the event is in the guest's event ring but the interrupt went
to the departing VMM's descriptor, so the guest was not told about it. We quote
the CH-clock lower bound as the headline and give the others so the reader can
see the spread; the truth lies between the lower and the epoch anchor.
The copy also continues for at least \SpanMarginMin\,s after the switchover
completes in the acceptance arm, so the criterion that the copy spans the whole
migration holds with a wide margin.

Whether such a missed interrupt is fatal depends on whether it is the
\emph{last} outstanding completion. The stick is a USB~2.0 Bulk-Only-Transport
device and the guest's mass-storage path keeps only a few commands in flight, so
if the completion of the final outstanding command is the one that lands in the
window, no further transfer is submitted and no later completion arrives to
interrupt the guest and drain the ring: the copy stops at a fixed byte count,
which is the stall we reproduced. If, on the other hand, more commands were still
queued, the next completion interrupts the guest on the new line. The guest then
drains the ring, including the events it was never interrupted for, and the same
exposure is harmless. That is why the defect is intermittent in the acceptance
runs rather than deterministic---and why the \emph{kick-off} arm of
Table~\ref{tab:arms} is a weak test on its own: it can only fail in the fraction
of runs where the missed completion happens to be the last one. The injection
suite of Section~\ref{sec:injection} makes that condition explicit.

\subsection{Fault injection at the hand-over}
\label{sec:injection}
The exposure measurement shows that the race happens on its own; it does not by
itself show that the two hand-over fixes are what make the system survive it. To
show that, we added two environment-gated hooks that exist only in debug builds:
one sleeps inside the \code{SetIrqs} handler for a configured time
\emph{before} the destination's line reaches the interrupter worker, and the
other makes every connection believe it owns the device, reintroducing the
stale-teardown defect. The first widens the hand-over window on demand; the
second disables the ownership guard.

The placement of the delay is the point. While \code{SetIrqs} sleeps, the
interrupter worker keeps draining completion events onto the departing client's
line---the window the kick exists to cover---and the transfer queue empties, so
that the completion which lands in the window is the last one outstanding. The
\emph{number} of completions at risk does not grow with the delay: it saturates
at the queue depth (a few per run, whatever the delay), because once
the queue is empty there is nothing left to complete. What the delay changes is
whether a \emph{further} completion follows the lost one. Sleeping in the worker
instead would push events behind the line-swap message and \emph{shrink} the
exposure rather than enlarge it. Two caveats about the hook's scope: it is not
restricted to the hand-over, so it also delays the source's own registration at
start-up (visible in the server log as a 500\,ms or 5\,s ``TEST HOOK'' line at
boot), and the sleep happens while the shared backend lock is held. Both are
irrelevant to the A/B contrast, which compares the same binary with the same
hook enabled and only the kick switched, but they are part of what the arm
measures. Table~\ref{tab:injection} gives the outcome; the VMM-side effect of
the delay is directly visible as downtime (the 5\,s arms report
$\approx$5\,s, and they are judged with the downtime budget raised to 12\,s
precisely because the injected delay \emph{is} the downtime there).

Three things follow. First, the hooks do nothing when they are not enabled
(\InjBaselinePass/\InjBaselineN), so the differences below are caused by the
injections and not by the build. Second, the \emph{ownership guard is
load-bearing and its absence is deterministically fatal}: with the guard
disabled the copy fails in all \InjGuardN{} runs
(\InjGuardPass/\InjGuardN{} pass; two-sided Fisher exact against the acceptance arm,
$p=\FisherGuard$), \code{dd} returns non-zero and the guest kernel logs a 36\,s
\code{DID\_TIME\_OUT} followed by repeated I/O errors---the source VMM's
teardown has replaced the destination's interrupt line with a dummy, so the
guest's commands never complete normally.

Third, the kick is what makes the hand-over survive a window that is wide enough
to matter. With a 500\,ms window the kick-enabled arm passes
\InjWindowPass/\InjWindowN{} and the kick-disabled arm passes
\InjWindowLossPass/\InjWindowLossN{} (two-sided Fisher exact, $p=\FisherWindow$). With a 5\,s window the
contrast is sharper still: \InjWinLongOnPass/\InjWinLongOnN{} against
\InjWinLongOffPass/\InjWinLongOffN{} (two-sided Fisher exact, $p=\FisherWinLong$). In every failing run
the copy stops at a fixed byte count and the guest sends no further completion
until a SCSI timeout expires, i.e.\ the observed failure is the mechanism the
kick prevents, not a generic timeout. Note that the kick-off arms are not
\emph{deterministically} fatal even at 5\,s---two of eight runs recovered---which
is consistent with the account in Section~\ref{sec:exposure}: a wide window
drains the queue and makes it likely, but not certain, that the lost completion
is the last one outstanding.

Three honesty notes. First, both extensions are \emph{post hoc}: the suite was
designed with four arms and predicted that the 500\,ms window without the kick
would fail. At the original five runs that prediction looked wrong (4/5 passed);
extending the arm to ten runs shows the effect (\InjWindowLossPass/\InjWindowLossN),
which is itself an illustration of why small arms mislead. We added the 5\,s
pair only after that, extended each arm to a fixed eight runs rather than
stopping when it looked good, and report both as exploratory. Second, we test
six contrasts (control, kick, window, winlong, guard, pre-fix), so a nominal
$p=0.05$ is not the right yardstick for any single one. Under a Holm correction
over those six, the guard ($p=\FisherGuard$) and the 5\,s pair
($p=\FisherWinLong$) survive and the 500\,ms contrast ($p=\FisherWindow$) does
not; we therefore treat the 5\,s result as the one that establishes the kick's
role and the 500\,ms result as nominal only. At eight runs per arm, with a
deliberately imperfect effect (5\,\% failure with the kick, 80\,\% without) the
5\,s arm has power $\PowerWinLong$; $\NPowerWinLong$ runs per arm would be needed
for 80\,\% power against that effect, so it is adequately powered for a large
effect and not for a small one. Third, the ownership hook disables both halves
of the guard, including the DMA-unmap half that our workload does not otherwise
exercise, so the arm demonstrates the guard as a whole rather than the two
halves separately.

One caveat is worth stating: the injection arms are mechanism tests, not
acceptance runs. They hold the workload fixed and change only the server's
behaviour through a dormant hook, but the enlarged window is synthetic, so the
arms establish that the fixes are necessary and sufficient \emph{for this
mechanism}; they do not measure how often the mechanism decides the outcome in
production.

\subsection{Discussion of the measurements}
Two points about the method are worth stating explicitly, because both changed
our conclusions during the work. First, host-side observation is not
sufficient: the packet capture and the VMM logs looked healthy in a run whose
guest had in fact stopped making progress. Second, a single passing run is not
evidence for a timing-dependent fix: the code without the fix of Section~\ref{sec:interrupt} passed four consecutive runs before the defect appeared on the fifth, and only repeated
runs after the fix justify the claim of \PassCount{} out of \TotalRuns{}.

%=====================================================================
\subsection{Threats to validity}
\label{sec:threats}
\emph{Construct.} The integrity check is an MD5 of a read-only bulk copy that
was read once, sequentially. It detects corrupted or lost data, but it cannot
detect \emph{duplicated} reads: a replayed read changes nothing in the
destination file. Our claim is therefore \emph{no data corruption and no lost
I/O}, and we do not claim to have tested duplication. The enumeration and
reset criteria are now derived from the guest's own kernel log and are counted
relative to the guest's uptime at the migration instant
(Section~\ref{sec:implementation}), which removes an earlier threshold artefact
in our harness, but they still rely on the kernel printing a message. It should
also be said that in this dataset they never decided a verdict on their own:
every failing run already failed the span or digest criterion, and the stalled
runs have no dmesg section at all, which the verdict treats as a failure rather
than as ``nothing happened''. The independent discriminating power of the two
kernel-log criteria is therefore demonstrated by construction (they fail
closed), not by a run they happened to catch.

\emph{Internal.} The host was loaded by four other VMs; a host-load sample is
archived with each batch, but it is not synchronised to individual runs. Run
order was not randomised and the arms were executed in blocks (acceptance,
control, release, kick-off), so a slow drift in host conditions would be
confounded with the arm---this is the single largest threat to the arm
comparison of Table~\ref{tab:arms}. The injection suite of
Section~\ref{sec:injection} is designed to be immune to it: it forces the
hand-over condition inside a single run and compares presence and absence of the
fix within one build, so its conclusions do not depend on cross-arm timing. The
server was a debug build with verbose logging and packet capture enabled, which
is why the release arm exists. The migration and pause instants used for the
``spans'' test are host-clock times; the guest's copy timestamps are compared
against them assuming the two clocks agree, and that assumption is not verified:
the heartbeat pairs check that the guest clock runs at the same rate, not that
its offset is zero. The exposure in the data is small---the nearest enumeration
or reset event is at least 6.9\,s from the cutoff in every migrating run, and the
span margin is at least \SpanMarginMin\,s in the acceptance arm---but the offset itself is untested. The destination of
the copy was a file on the host-backed guest disk, so host page-cache writeback
is in the loop.

\emph{External.} One device class (bulk storage), one USB~2.0 Bulk-Only
Transport device on one controller, one guest kernel, one workload size, and
same-host \code{memfds} migration only. A USB~3.0/UAS device with several
in-flight commands would exercise the hand-over differently, and the slow
transfer of the stick used here (128\,MiB in \CopyMin--\CopyMax\,s, roughly
4--10\,MiB/s) makes a completion less
likely to land inside the hand-over window than it would be on faster hardware.

\emph{Statistical.} $n=\TotalRuns{}$ in the acceptance arm and $n=5$ for the
pre-fix rate, so the confidence intervals are wide. The natural kick comparison
has power $\PowerKickNatural$ and would need about $\NKickForEighty$ runs per
arm to reach 80\,\% at the observed effect; the 5\,s injection pair reaches
$p=\FisherWinLong$ at $\InjWinLongOnN$/arm but has power $\PowerWinLong$ against
an imperfect effect. Section~\ref{sec:results} and Section~\ref{sec:injection}
give the full statement, including that the 5\,s pair was added after the
500\,ms arm contradicted its prediction and is therefore exploratory.
The pre-fix five-run series is described in the development log; its raw logs
predate the archiving harness and are not part of the attached evidence, so the
pre-fix comparison should be read as qualitative.

\section{Discussion and Limitations}
\label{sec:discussion}
%=====================================================================

\paragraph{What is transparent.}
At the USB level the guest is undisturbed: it enumerates the device once, at
boot, and never again; it observes no reset, no port status change and no I/O
error; the file it copies is byte-identical to the source. This is the property
that matters for storage passthrough and it is the one we set out to obtain.

\paragraph{What is not transparent.}
One guest-visible disturbance remains and we do not want to hide it: after the
migration the guest reprints its login banner. The destination re-creates the
serial device, which resets the guest TTY. This is a property of the VMM's
serial device model, not of the USB path, and it does not affect the device. We
report it because a claim of ``zero perception'' should be stated at the
granularity at which it is true.

\paragraph{No explicit quiesce.}
We did not implement a bounded drain of in-flight transfers before the
hand-over. Transfers in flight when the migration happens are handled by the
re-raise mechanism: the injected 5\,s-window experiment
(Section~\ref{sec:injection}) shows that without that one re-raised interrupt the
guest can wait indefinitely for a completion that has already been written to
its event ring, and that with it the copy continues even when the window is
two to three orders of magnitude wider than the natural one. What we cannot claim is
that a transfer is never retried: an explicit quiesce would make the in-flight
set empty by construction and remove the dependence on where in the command
queue the hand-over lands.

\paragraph{Scope.}
The evaluation covers bulk storage on a USB~2.0 stick, one device per
controller, Linux guests, and same-host migration. Other classes (HID,
isochronous audio, serial) have different in-flight semantics; isochronous
traffic in particular cannot be made lossless by retrying and is not supported
by the underlying \code{nusb} library. Cross-host migration is a different
problem: it needs the device state to be transferred or an equivalent device to
be provided on the destination, and it cannot preserve a host-side session.

\paragraph{Failure and rollback.}
Ownership of the device is decided by whichever connection most recently
registered interrupts, and it is not committed to a migration transaction. If a
migration is cancelled after the destination has installed its line, the source
is left running with a line that will not be serviced, and nothing re-registers
it. Our own Phase-0 measurements showed that CH's
\code{timeout\_strategy=cancel} did not in fact bring the source back to a
usable state. A production design needs an explicit epoch that is committed at
migration commit time, plus a revoke and re-register path, and it needs to be
tested with a destination crash and a source-side cancel while I/O is in
flight. We did not implement or test that.

\paragraph{Socket trust and bounds.}
The vfio-user socket grants whoever can connect it full DMA authority over the
guest's memory, so it is as sensitive as the guest's own memory. Our accept
loop bounds how many connections are \emph{served} (\code{-{}-max-clients}), but
a client beyond that limit waits in the listen backlog, there is no per-client
timeout, and a client that registers interrupts becomes the owner and may then
unmap DMA regions. A deployment must therefore treat the socket as trusted and
protect it with filesystem permissions or a private namespace; the design does
not defend against a hostile local client.

\paragraph{Process lifecycle.}
With more than one client the server no longer exits when the last client
disconnects, which is a deliberate change needed for the hand-over. Deployments
that rely on exit-on-disconnect (for example socket-activated systemd units)
must either keep the default single-client mode or manage the process
explicitly.

\section{Conclusion and Future Work}
\label{sec:conclusion}
%=====================================================================

We set out to make a USB storage device survive a live migration of the VM it
is passed through to, and we found that the path did not merely fail---it
deadlocked, because a vfio-user server built for one client cannot serve the
destination while the source is still attached. The fix follows from a
property of the protocol that is easy to miss: the handshake does not touch the
device, so the device lock does not have to be held for the lifetime of a
connection. On top of that, two further defects had to be fixed before the
hand-over was correct rather than merely possible: ownership of destructive
teardown, and the synchronisation of the interrupt line across the hand-over.
With those in place, a 128\,MiB copy that spans the migration completes in
\PassCount{} out of \TotalRuns{} runs with \DowntimeMin--\DowntimeMax\,ms of
downtime and byte-identical data; the kick-disabled and guard-disabled
injections, and the enlarged-window injections, show that both hand-over fixes
are load-bearing rather than incidental.

Future work falls into three groups. First, an explicit quiesce and a
guest-cooperative protocol would make in-flight behaviour deterministic instead
of relying on retry. Second, a protocol-level device-state region would allow
the device to be reconstructed on another host, which is the prerequisite for
cross-host migration; our measurements show that the current protocol carries
none of the required state. Third, the same technique should be evaluated for
other device classes and for multiple devices on one controller, where the
ownership rules we introduced would need to become per-device.
